## 2. 看什么（不预设分类，记录原始观察）

**先不建立固定分类体系**（本人已定：随实践慢慢结构化）。看到什么记什么，但每条观察要写清：

- **现象**：到底发生了什么（不要写「流程不顺」这种空话）
- **位置**：文件路径 / commit / 事项 id / 会话文件（能给就给，方便回查）
- **损失**：它让你多花了几次往返、多少返工、还是直接做错了

找的是**反复出现的模式**，不是一次性事故。同一个现象出现两次以上，才值得写进建议。
优先看这些地方（只是入口，不是分类）：同一件事开了多次会话、同一条约束被踩多次、
同一类 bug 修多次、方案里已经写下的决定在实现时又被推翻、会话问完话没人回。

## 3. 写什么（报告落点与结构）

写到：`{{report}}`（一次性生成；**永久保留**，不覆盖、不滚动合并）。

```markdown
# 复盘 {{date}}

## 观察（原始，不分类型，看到啥记啥）
- <现象> —— 位置：<文件/commit/事项/会话>；损失：<往返次数 / 返工 / 错误>

## 建议（每条写清：改哪里、改成什么）
### #<id> <一句话标题>
- 改哪里：<文件 / 机制 / 流程>
- 改成什么：<具体到能照着做；只写「要改进」等于没写>
- 依据：<对应上面哪条观察>

## 采纳跟踪（上一天的建议，哪些真改了）
- #<id> <标题> → 已采纳 / 已否决 / 搁置（附一句为什么）
```

## 4. 每条建议要进复盘账本（供采纳跟踪）

报告里写完，**逐条**把它记进复盘账本（与 `items.jsonl` 分开，别混）：

```
node {{cli}} add "<建议标题>" --target "<改哪里>" --change "<改成什么>" --evidence "<依据>"
```

命令会打印建议的 `#id`。**把同一个 `#id` 写进报告的 `### #<id>` 标题里** ——
这样报告和账本对得上，「采纳」才度量得了。

## 5. 采纳跟踪（先结掉旧建议）

先读上一天（及更早）还挂着的建议：

```
node {{cli}} list --status pending
```

对每一条，去查它到底改没改（git log 里有没有那次改动、对应文件现在长什么样），然后结掉：

```
node {{cli}} status <id> adopted  --note "<哪个 commit / 哪个文件改了>"
node {{cli}} status <id> rejected --note "<为什么不做>"
node {{cli}} status <id> parked   --note "<为什么先搁置>"
```

**只标状态，不要替本人做改动。** 拿不准改没改，就标 `parked` 并写清疑点，别猜。
